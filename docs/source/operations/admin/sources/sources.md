# 📥 Sources

Sources define the ingestion boundary for EdgeStream Hub. They act either as network listeners (binding to local ports to receive telemetry from agents, sockets, or push APIs) or as active collectors (polling remote cloud endpoints, queues, and object storage systems).

## Supported Source Types

EdgeStream Hub leverages high-throughput Vector pipeline architecture to ingest structured and unstructured telemetry across standard network protocols and cloud brokers.

- Office 365 Audit (o365audit): Polls the Office 365 Management Activity API to ingest audit and security telemetry across Microsoft 365, Entra ID (Azure AD), and Microsoft Purview.

    Supported feeds include:
    - Audit.General (Teams, Sway, Planner, Yammer, Defender alerts)
    - Audit.AzureActiveDirectory (User identity, tenant role assignments, sign-ins)
    - Audit.Exchange (Mailbox access, administrative actions)
    - Audit.SharePoint (Document libraries, access modifications, OneDrive actions)
    - DLP.All (Data Loss Prevention rule matches and security incidents)
    <br><br>

- AWS SQS (aws_sqs): Pulls discrete messages from Amazon Simple Queue Service (SQS) standard or FIFO queues for decoupled asynchronous processing.
<br><br>

- AWS S3 (aws_s3): Ingests bulk log files and objects stored in Amazon S3 buckets, orchestrated via SQS bucket notification polling.
<br><br>

- CEF (cef): Binds a TCP/UDP socket listener to ingest and parse Common Event Format (CEF) log streams generated by security appliances, firewalls, and SIEM forwarders.
<br><br>

- Fluent (fluent): Implements a native Fluentd/Fluent Bit forward listener supporting Forward protocol payloads over TCP.
<br><br>

- File (file): Actively monitors and streams line-delimited log files directly from the underlying appliance host filesystem.
<br><br>

- Host Metrics (host_metrics): Scrapes host-level system metrics from the EdgeStream Hub appliance (CPU usage, memory footprint, load averages, disk I/O, and interface statistics).
<br><br>

- HTTP Client (http_client): Actively scrapes or polls remote HTTP/HTTPS API endpoints on scheduled intervals to pull structured telemetry or JSON documents.
<br><br>

- HTTP Server (http_server): Hosts a webhook and REST endpoint listener accepting inbound events and payloads over HTTP/HTTPS POST requests.
<br><br>

- Internal Metrics (internal_metrics): Emits operational runtime telemetry and performance counters from the EdgeStream Hub pipeline engine itself (event processing throughput, latency, component error rates).
<br><br>

- Logstash (logstash): Implements an Elastic Lumberjack protocol listener compatible with Elastic Beats agents (Winlogbeat, Filebeat, Metricbeat).
<br><br>

- NetFlow (netflow): High-performance UDP datagram receiver and parser supporting Cisco NetFlow v5, v7, v9, and IPFIX formats.
<br><br>

- OpenTelemetry (opentelemetry): Hosts an OTLP-compliant receiver accepting traces and logs via gRPC or HTTP transport.
<br><br>

- PostgreSQL Metrics (postgresql_metrics): Polls PostgreSQL database engines to collect cluster health, query execution performance, buffer utilization, and connection stats.
<br><br>

- Raw Socket (socket): Generic, high-throughput network listener binding to TCP, UDP, or Unix domain sockets for raw streaming data.
<br><br>

- Splunk HEC (splunk_hec): Emulates the Splunk HTTP Event Collector API to ingest events directly from systems with preconfigured Splunk outputs.
<br><br>

- Syslog (syslog): Ingests RFC 3164 (BSD) and RFC 5424 (IETF) structured syslog datagrams and streams across UDP, TCP, or TLS.
<br><br>

- Vector (vector): Native point-to-point Vector protocol listener optimized for streaming events between EdgeStream nodes or upstream Vector topologies.
<br><br>

- Windows Event Collector (wec): (Coming Soon) Integrated Windows Event Forwarding (WEF) subscription service for agentless log collection from domain-joined Windows endpoints.
<br><br>

## Metadata Tagging & Enrichment

Every event ingested into EdgeStream Hub is enriched at the ingestion boundary with core routing metadata:

| Metadata Field | Value Example | Purpose | 
|----------------|---------------|---------|
| @edgestream.event.name | core_firewall_syslog | The unique administrative identifier assigned to the source instance. Used for pipeline routing and filtering. | 
| @edgestream.event.src_type | syslog | The architectural source type handling the data ingestion. | 

## Provisioning a Source

1. Navigate to Administration → Configuration → Sources.

2. Click Create in the top navigation actions.

3. Configure the source definition:

    - Enabled: Toggle whether the pipeline component initializes immediately upon creation. If set to disabled, configuration state is stored without binding network ports or initiating background polling jobs.
   
   - Name: A unique, alphanumeric identifier (e.g., prod_aws_sqs_ingress).
   
        ```{note}
        Identifier Immutability: Source names cannot be altered after creation because internal pipelines, downstream filter stages, and destinations bind directly to this identity. To rename a source, provision a new source with the desired name and decommission the old entry.
        ```

    - Type: Select the matching source type from the catalog.

        ### Configuration Sections

        The drawer populates dynamic configuration blocks based on the selected type:

        - Base Settings (Mandatory): Required connection settings (e.g., socket address, listening port, bucket name, queue URL, or authentication strategy). Pre-flight checks run on socket addresses to prevent port collisions with host services or existing listeners.

        - TLS Settings (Conditionally Available): For network-facing listeners and outbound API clients, configure encryption parameters including server certificates, private keys, custom Certificate Authority bundles, and mTLS client-verification policies.

        - Optional Settings: Advanced parameters allowing fine-tuning of parsing options, multiline aggregation timeouts, receive buffer overrides (SO_RCVBUF), CIDR origin restrictions (permit_origin), and character set decoding. When left unconfigured, system defaults apply.
    
4. Click Create to deploy the configuration.

## Routing to Destinations

By default, an isolated source does not automatically deliver data to outbound systems:

- Default Sinks: If an appliance-wide default destination is configured, newly created sources forward traffic to that egress pipeline automatically.

- Explicit Sink Association: To establish dedicated egress paths, navigate to Administration → Configuration → Destinations, edit the desired output sink (e.g., S3, ClickHouse, Kafka), and select the new source name within the Inputs / Events and Metrics association list.

```{note}
Unassigned sources without a default sink or an explicitly bound destination pipeline will ingest events and drop them at the pipeline terminus (blackholed).
```

## Lifecycle Operations

- Modifying a Source: Click Edit adjacent to any listed source to adjust ports, update credentials, change parsing parameters, or toggle the component's Enabled status.

- Deleting a Source: Click Delete to unbind sockets, stop polling daemons, and remove the pipeline component. Verify that no critical destination sinks or transformation filters depend on the selected source prior to deletion.
